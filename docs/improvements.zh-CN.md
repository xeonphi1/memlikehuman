# 下一轮改进与验收标准

基于 2026-11-10 的代码检查。按影响正确性、用户可见性和维护成本排序；未完成项是后续工作，不代表现有能力。

## 本轮完成：自动捕获与 MCP 使用同一分区

- `serve` 继承全局 `--persona` / `--project`，并在初始化说明、七个工具的参数默认值、会话提示中统一呈现。
- DSH bundle 传递配置分区；模型漏传参数不再读写 `default/default`。显式参数仍然覆盖默认值；旧分区不迁移。
- 自动捕获模式使用 `serve --host-capture`，移除要求模型再次逐条记录的服务指令。手动 MCP 模式保留原调用流程。
- setup 在写配置和运行数据库检查之前验证 Python 是否支持新启动选项。
- 回归覆盖真实 stdio 的省略参数、显式分区、跨分区读取失败、工作恢复、纠错与删除，以及自动/手动两种指令。

## 1. 让用户看见捕获是否健康

现状：宿主失败时只有日志警告，数据库有 `host_cursors` 记录，网页尚未展示捕获进度。用户很难判断“已安装”和“正在可靠记录”的区别。

建议：网页按人格/项目展示最近确认的会话位置、持久化时间、失败类别与重试状态；日志不包含对话原文。配置或依赖错误应直接给出可执行的修复步骤。

验收：错误程序路径、写入超时、正常恢复、重启续传都可见；失败时不推进游标；没有运行适配器时不能显示为“正常捕获”。

## 2. 让历史提炼可预估、可暂停、可续跑

现状：`retry --limit` 已能分批处理 pending 事件，但网页只提供人工提炼；用户不容易看出还剩多少、哪些失败、会向哪个提供商发送哪些内容。

建议：先提供离线队列概览和 dry-run；用户明确启动后再处理指定分区与批次。记录成功/失败数，失败隔离，避免一个长任务占住聊天路径。不默认启用后台付费请求。

验收：中断后续跑不重复提炼已完成事件；未确认前无外部请求；显示提供商、范围及待处理规模，能暂停且已提交数据不回滚。

## 3. 建立检索质量基准

现状：已有检索延迟基准与规则测试，但缺少系统衡量“找对记忆”的固定问题集。

建议：用合成中文长历史构造问答集，覆盖事实变更、同名事件、时间限定、否定、未确认偏好、旧原文及跨项目干扰；同时报告来源命中率、Top-k 召回和错误分区命中。关键词和语义模式使用同一组样本。

验收：每个回答能指向预期原文；跨分区命中为零；性能或排序改动必须同时说明质量指标变化，不能只报告毫秒数。

## 4. 收敛长历史捕获成本

现状：每次 flush 先启动 Python 查询游标，分批写入时继续启动子进程。当前 `WeakMap` 会串行排队，但密集事件与周期 flush 仍可能造成重复检查。

建议：先测量高频会话的进程数和尾部延迟，再合并同会话冗余 flush 请求；保留压缩前后 checkpoint 的严格顺序。确认收益后才考虑常驻桥接进程。

验收：强杀、重启、磁盘失败、多个分区并行时不跳过事件；压缩等待持久化；报告每百轮子进程次数与 P95 写入延迟。

## 5. 防止多个网页编辑窗口覆盖人格修改

现状：提炼记忆的并发修订已有旧版本撤销检查，但人格编辑仍直接新增版本；旧页面可以把后来修改的人格内容重新写成最新版本。

建议：人格编辑提交读取时的版本号，数据库事务内校验，不一致时返回冲突并保留用户草稿；明确的历史回退仍作为独立操作。

验收：两个窗口同时编辑时，第二个保存收到冲突；刷新后可比较和重新提交；不能静默把新版本替换成旧页面内容。

以上工作继续沿用 GitHub 源码分发，不以发布 npm 或引入云服务为前提。
